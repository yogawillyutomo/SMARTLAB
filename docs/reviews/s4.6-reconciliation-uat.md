## 2. Migration/import policy — classification only

No automatic browser-data migration is approved by S4.6.

A future explicitly approved import/reconciliation tool must classify every candidate record into exactly one of these outcomes:

| Classification | Meaning | Allowed action |
| --- | --- | --- |
| `exact_safe_match` | one canonical same-School target is proven by stable evidence and all required dependencies agree | may be proposed for explicit import/apply; never infer identity from the browser ID |
| `unmatched` | no canonical target can be proven | preserve as unresolved evidence; do not fabricate a target |
| `ambiguous` | more than one plausible canonical target exists | block automatic apply; require human reconciliation |
| `invalid` | payload/value/scope violates the canonical contract | reject and report the reason |
| `blocked_by_dependency` | the record could be valid but a required canonical dependency is missing or unresolved | defer until dependency reconciliation succeeds |

Hard rules:

- browser/local IDs never become server ULIDs by inference;
- display name alone is never sufficient identity;
- cross-School matching is prohibited;
- Stock quantity becomes an explicit opening/receipt/adjustment transaction, never a hidden balance write;
- historical Loan/Maintenance text that cannot map to an exact Asset remains historical/unresolved evidence;
- S4 import cannot create Work Orders or Incidents implicitly.

### Preconditions

- record the exact deployed commit SHA;

- use canonical server test records that can be safely modified;
- do not run destructive scenarios against production data;

### Reset procedure

1. sign out if needed;
2. clear site Local Storage;
3. clear IndexedDB/site databases used by the SMARTLAB origin;
4. clear Service Worker/cache storage if present;
5. start a fresh authenticated session;
6. hard reload the application;
7. confirm no seed/local business records reappear.

### Route matrix

| Route | Required observation after storage clear | Suggested safe mutation | Reload/deep-link proof |
| --- | --- | --- | --- |
| `/assets` | list/detail loads canonical server Assets only | create/update a dedicated UAT Asset if permission allows; query operational-state evidence through API/devtools as needed | hard reload/detail deep link returns the same server record |
| `/stock` | item list and immutable movement history load from server | receipt/issue a dedicated UAT InventoryItem with a new clientMutationId | reload shows persisted balance/history; no local quantity resurrection |
| `/loans` | Loan list loads from server and exact Asset selection is canonical | submit a dedicated UAT Loan; perform only lifecycle actions the operator is authorized to perform | reload preserves Loan/version/status and exact LoanItems |
| `/maintenance` | plans/executions load from server and exact Asset selection works | create/schedule a dedicated UAT preventive plan/execution; do not fabricate corrective Work Order activity | reload preserves plan/execution evidence and server lifecycle |

### Explicit fail conditions

Any of the following is an S4 UAT failure:

- a canonical route becomes empty/broken solely because browser business storage was cleared;
- seed Asset/Stock/Loan/Maintenance records reappear as operational truth;
- a mutation appears successful but disappears after reload;
- local state overrides a newer server version;
- a route uses compatibility role logic as authorization authority;
- Asset/Inventory/Loan/Maintenance records from another School become visible;
- Loan and Maintenance become active simultaneously for one Asset;
- a stock movement produces a negative balance;
- a Maintenance/Loan action mutates Device lifecycle/home Laboratory implicitly;
- S4 UI creates a Corrective Work Order as an implicit side effect.
