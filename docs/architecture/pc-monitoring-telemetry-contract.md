# LARAS PC Monitoring Telemetry Contract

**Status:** DRAFT / PROPOSED — planning-only; not implementation authority until S5.6 closes and ADR-004 is accepted  
**Target phase:** S6 — PC Monitoring Telemetry

## 1. Goals

S6 turns the existing server-authoritative Device inventory and `/monitoring` workspace into safe near-realtime PC health monitoring.

It must provide:

- authorized enrollment and immediate revocation of one Windows agent installation for one exact Device;
- machine authentication independent from human browser sessions;
- approved heartbeat/health telemetry ingestion;
- bounded offline buffering and idempotent replay;
- efficient latest-state and bounded-history reads;
- Global Laboratory Context-aware monitoring UI;
- explicit privacy and no-surveillance guarantees.

It must not create a second Device authority or a remote-control platform.

## 2. Authority model

### Canonical Device

`Device` remains authority for Device identity, School ownership, lifecycle, home Laboratory, canonical technical profile, and human-managed metadata.

### Agent installation

`DeviceAgentInstallation` is machine-auth authority only. It proves that one revocable agent credential is currently allowed to submit telemetry for one exact Device.

An installation cannot transfer itself to another Device or School. Device transfer between Laboratories does not require agent re-enrollment because the installation follows the canonical Device; monitoring read scope resolves the Device's current Laboratory at read time.

### Telemetry

Telemetry is observational evidence. It never mutates canonical Device/Asset/operational domains implicitly.

## 3. Proposed persistence

### `DeviceAgentEnrollment`

Purpose: short-lived, human-authorized bootstrap for one exact Device.

Minimum evidence:

- ULID;
- `school_id`;
- `device_id`;
- hashed one-time enrollment code;
- status: `pending | redeemed | expired | revoked`;
- creator membership/user snapshots;
- `created_at`, `expires_at`, nullable `redeemed_at`/`revoked_at`;
- optional revoke reason.

Rules:

- code contains >=128 bits of cryptographic randomness;
- server stores only a one-way code hash;
- default expiry proposal: 10 minutes;
- redemption is single-use and serialized;
- at most one pending enrollment per Device is preferred for v1;
- expired/redeemed codes are never reusable.

### `DeviceAgentInstallation`

Purpose: durable revocable machine identity for one exact Device.

Minimum evidence:

- ULID installation ID;
- exact `school_id` + `device_id` binding;
- status `active | revoked`;
- credential version/identifier;
- one-way secret hash;
- enrolled/revoked actor snapshots and timestamps;
- revoke reason;
- agent version last seen;
- `last_authenticated_at`.

Rules:

- at most one active installation per Device in S6 v1;
- credential secret is never readable after issuance;
- replacement/re-enrollment revokes the old active installation transactionally;
- revoked installation cannot submit heartbeat, metrics, inventory, or configuration reads;
- terminal/ineligible Device lifecycle rejects machine ingestion without changing Device lifecycle.

### `DeviceTelemetryLatest`

Purpose: mutable projection for low-cost monitoring lists/details.

Suggested fields:

- installation/device IDs;
- server `last_received_at`;
- last accepted agent `observed_at`;
- `boot_id` + sequence;
- CPU percentage;
- memory used/total bytes;
- system/fixed-volume disk free/total summary;
- aggregate network receive/transmit counters or rates;
- uptime seconds;
- latest hardware-snapshot hash;
- latest agent version;
- dropped-buffer count reported after reconnect.

This is a projection and may be overwritten by a newer accepted observation. It is not an audit log.

### `DeviceTelemetrySample`

Purpose: append-oriented bounded history.

Minimum fields:

- ULID row ID;
- installation/device binding;
- random `sample_id` generated by agent;
- `boot_id` + monotonic sequence;
- agent `observed_at`;
- server `received_at`;
- CPU percentage;
- memory used/total bytes;
- disk summary;
- aggregate network counters/rates;
- uptime seconds.

Unique `(installation_id, sample_id)` makes retries idempotent.

Default retention proposal: 30 days raw.

### `DeviceHardwareSnapshot`

Purpose: append-oriented observed OS/hardware state when the normalized snapshot changes.

Allowed snapshot content:

- OS name/version/build/architecture;
- CPU model and core counts;
- total RAM capacity;
- fixed-disk model/capacity;
- GPU/display adapter model where available;
- agent version/snapshot schema version.

It must not contain usernames, MAC-address identity authority, browsing/application/process data, document names/content, or personal content.

Observed hardware never auto-updates `Device.technicalProfile`.

## 4. Human permissions

Proposed new permissions:

- `telemetry.view` — read latest/history telemetry;
- `devices.manage-agent` — create enrollment codes and revoke/replace agent installations.

All monitoring reads also remain bounded by canonical Device visibility and active SchoolMembership.

Proposed baseline grants for later catalog review:

| Role | `telemetry.view` | `devices.manage-agent` |
| --- | --- | --- |
| `admin-lab` | yes | yes |
| `kepala-lab` | yes | no |
| `teknisi` | yes | yes |

| `pimpinan` | no by default | no |

## 5. Proposed human API

Exact routes remain subject to OpenAPI lock, but the initial shape is:

- `POST /devices/{deviceId}/agent-enrollments` — create one-time enrollment code;
- `GET /devices/{deviceId}/agent-installations` — read installation/revocation history;
- `POST /device-agent-installations/{installationId}/revoke` — revoke immediately with reason;
- `GET /monitoring/devices` — Device + latest telemetry projection, Global Lab-scoped;
- `GET /devices/{deviceId}/telemetry/latest` — latest accepted telemetry;
- `GET /devices/{deviceId}/telemetry/history` — bounded historical samples.

Human endpoints use existing Sanctum/SchoolMembership/RBAC boundaries.

## 6. Proposed machine API

Machine routes use dedicated machine-auth middleware and no browser session authority.

### Bootstrap

`POST /pc-agent/v1/enroll`

Input contains only the single-use enrollment code plus non-authoritative agent metadata needed to establish compatibility. The server resolves exact School/Device from the code.

Successful response returns once:

- installation ID;
- credential identifier + secret;
- heartbeat/metric/buffer policy;
- API schema/version compatibility.

### Lightweight heartbeat

`POST /pc-agent/v1/heartbeat`

Authenticated by installation credential. Updates only server receive freshness and bounded current metadata. No historical `online` backdating is allowed.

### Metric replay

`POST /pc-agent/v1/telemetry/batch`

Authenticated, bounded batch of zero or more metric samples and optional changed hardware snapshot.

Proposed limits:

- max 100 samples/request;
- sample age <=24 hours;
- future clock skew <=5 minutes;
- explicit request-body cap;
- strict numeric/schema validation;
- duplicate `sampleId` replays return idempotent success/no duplicate row.

### Agent policy

`GET /pc-agent/v1/config`

Returns non-secret policy such as:

- heartbeat interval;
- metric interval;
- maximum offline-buffer horizon;
- maximum batch size;
- minimum supported agent version when enforcement is later required.

It never returns remote commands in S6 core.

## 7. Telemetry cadence and derived status

Default proposal:

- heartbeat interval: 60 seconds;
- metric interval: 300 seconds;
- browser monitoring refresh while visible: 30 seconds;
- offline history buffer: 24 hours / 288 metric samples;
- telemetry batch maximum: 100 samples;
- raw metric retention: 30 days.

Derived connectivity status:

- `not_enrolled`: no active installation;
- `revoked`: most recent installation revoked and no active replacement;
- `online`: active installation, last server receive age <=150 seconds;
- `stale`: >150 and <=600 seconds;
- `offline`: >600 seconds.

These defaults should be configuration policy rather than scattered magic numbers.

## 8. Validation rules

At minimum:

- CPU percent finite and 0..100;
- memory totals nonnegative and used <= total;
- disk totals nonnegative and free <= total;
- network counters/rates nonnegative;
- uptime nonnegative;
- sequence nonnegative and bounded;
- `observed_at` cannot exceed allowed future skew;
- buffered sample age cannot exceed backfill policy;
- batch length/body size bounded;
- agent version/schema strings length-bounded;
- unknown fields rejected on machine payloads unless versioned contract explicitly allows them.

The server owns `received_at`, School scope, Device scope, credential state, retention, and connectivity status derivation.

## 9. Privacy contract

Approved:

- device/service health;
- aggregate resource utilization;
- non-user OS/hardware inventory.

Rejected by contract:

- input/content capture;
- screen/audio/video capture;
- browser/network destination history;
- packet payloads;
- file/document contents or browsing of personal directories;
- process lists;
- installed-app inventory in S6 v1;
- username/activity tracking;
- clipboard;
- arbitrary command output.

A future request for any new field must update the telemetry contract, state privacy rationale, add negative tests, and receive explicit review before collector implementation.

## 10. Windows agent local behavior

Target runtime: Go Windows service.

Proposed local directories:

- service configuration: `%ProgramData%\\LARAS\\agent\\config.json` (non-secret);
- encrypted credential: service-owned file under `%ProgramData%\\LARAS\\agent\\`, protected by DPAPI LocalMachine and restrictive ACLs;
- bounded queue: service-owned local database/file under `%ProgramData%\\LARAS\\agent\\queue\\`.

Operational behavior:

1. service starts;
2. decrypts credential;
3. loads server policy;
4. emits heartbeat;
5. samples approved metrics on policy cadence;
6. buffers while offline;
7. retries with exponential backoff + jitter;
8. replays bounded batches after reconnect;
9. stops sending immediately when server rejects revoked/invalid credential and records a local operator-visible error.

No interactive user session is required for normal service operation.

## 11. Monitoring read model / UI

The current `/monitoring` page already consumes canonical Device inventory and Global Laboratory Context. S6 replaces placeholder realtime cells with server telemetry only.

List/card fields should include:

- Device code / hostname;
- current Laboratory from canonical Device;
- Device lifecycle;
- enrollment state;
- online/stale/offline status;
- last seen;
- CPU/memory/system disk latest summary;
- agent version/update state where approved.

Detail view may add:

- latest metrics;
- bounded 24h/7d/30d history charts;
- observed OS/hardware snapshot;
- canonical-vs-observed drift indicators;
- enrollment/revocation evidence for authorized managers.

Rules:

- no random/mock realtime values;
- missing telemetry renders explicitly as unavailable/not enrolled;
- Global Laboratory Context filters by canonical Device home Laboratory, not agent-supplied scope;
- frontend permission guards are convenience only; server remains security authority.

## 12. Data volume and retention

With 5-minute samples:

- 100 devices: 28,800 samples/day;
- 200 devices: 57,600 samples/day;
- 500 devices: 144,000 samples/day (~4.32M/30 days).

Initial design intentionally uses PostgreSQL plus indexes and retention cleanup rather than adding a time-series database dependency before evidence demands it.

Potential future optimizations:

- daily/hourly rollups;
- table partitioning;
- asynchronous ingestion;
- Redis/SSE/WebSocket presentation.

None are required merely to start S6 safely.

## 13. No automatic side effects

Telemetry changes no canonical Device/Asset/Incident/WorkOrder state by itself.

A high CPU/disk condition may be displayed as a transient health badge, but persistent alerting/notifications and analytics remain S7 concerns unless explicitly accepted later.

## 14. Update policy

S6 must define update safety even if auto-update is deferred:

- manual/admin-controlled deployment is the default;
- no unsigned executable is installed by the service;
- no arbitrary update URL is accepted from telemetry payloads;
- future auto-update requires signed artifacts, trusted key pinning, version/rollback policy, integrity verification, and explicit implementation/UAT.

## 15. Implementation slices after S5.6 closure

- **S6.1 — Contract + threat model lock:** accept ADR-004, exact schemas/routes/permissions/retention, OpenAPI draft.
- **S6.2 — Machine identity + enrollment/revocation:** persistence, one-time enrollment, credential auth, permission catalog, concurrency/security tests.
- **S6.3 — Telemetry ingestion + read models:** heartbeat, samples, hardware snapshots, latest projection, history, retention, idempotency, PostgreSQL load/concurrency tests.
- **S6.4 — Go Windows agent MVP:** Windows service, DPAPI secret storage, collectors, bounded queue, backoff, heartbeat/batch clients, service lifecycle tests.
- **S6.5 — Monitoring frontend cutover:** real server telemetry in `/monitoring`, history/detail UX, Global Lab Context, permission-safe enrollment management.
- **S6.6 — Security/privacy/operational UAT:** real Windows installation, offline/reconnect, revoke/re-enroll, cross-School, privacy inspection, resource/load evidence, exact-head CI/deployment.

Signed automatic update implementation is not required for S6 closure unless later explicitly promoted into scope; the update policy itself is required.

## 16. Implementation gate

No S6 implementation branch should be opened from this planning branch until S5.6 runtime/privacy/physical-scan gates are complete and PR #90 is merged. After that, rebase is **not** assumed; create a fresh S6 implementation branch from the verified merged `main` and port/merge only the accepted planning documents normally.
